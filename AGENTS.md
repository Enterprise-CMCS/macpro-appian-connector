## Learned User Preferences

- Open pull requests against `master`.
- Do not add a frontend page, banner, or feature flag for credential-change downtime unless directed.
- Prefer unit tests over extensive inline documentation.
- In `src/services/connector/libs/connectors.ts`, write each connector's JDBC settings inline. Duplicated connection values are intentional; do not extract a shared connection config.
- Write daily summaries as plain-text `.txt` files (not Markdown or PDF) for pasting into Teams, aimed at a less technical audience, in no more than three paragraphs.
- Ask before AWS writes, git pushes to shared branches, and release PR merges unless explicitly directed.

## Learned Workspace Facts

- Connector DB details live in AWS Secrets Manager, not SSM. Master reads `appian/master/dbInfo`; ephemeral deploys fall back to `appian/default/dbInfo`. Business-directed stage-to-schema mapping: bigmac-dev/master uses `MACPROTEST1`, bigmac-val will use `MACPROVAL0`, and bigmac-prod will use `MACPROP` (val/production are plan-of-record only until their view/table, grant, and network gates are confirmed). Master was cut over to `MACPROTEST1` on 2026-10-28: the user updated bigmac-dev's `appian/default/dbInfo` and `appian/master/dbInfo` to the same MACPROTEST1 values (the master secret's previous version retains the earlier Dev1 values as rollback). Val reads `appian/val/dbInfo` and production reads `appian/production/dbInfo`. JSON fields are `ip` (host), `port`, `db` (Oracle SID in the thin JDBC URL), `user` (login), `schema` (table qualifier), and `password`. Do not commit concrete `user`, `schema`, `db`, password, host, account ID, ARN, or EventBridge physical name values. The MACPro application login is separate from the connector login. The master/dev Oracle database is in a separate MACPro account (use the `appian-dev` profile for read-only investigation there), so database networking changes use that account rather than the `bigmac-dev` profile. Leave the val account’s separate `appian/default/dbInfo` unchanged.
- Database username and password changes are manual; do not reintroduce an automatic password updater. Full steps: https://confluenceent.cms.gov/pages/viewpage.action?pageId=1504366491. Do not commit account IDs, secret values, ARNs, or EventBridge physical names. `configureConnectors` reads `legacydbPassword` from its Lambda environment (set at deploy), not Secrets Manager at runtime; it reads connector status once after the config PUT, throws on auth/lock traces without restarting, does not poll, and does not change the dbInfo secret. Connector status reads normalize a non-status/404 body (e.g. a just-created connector) to `NOT_FOUND` with no tasks, so callers do not crash on undefined fields.
- The master stage is the dev environment; ephemeral branches deploy there. A push to `master` auto-opens a release PR to `val`, and a push to `val` auto-opens one to `production`. AWS CLI profiles: `bigmac-dev` (master), `bigmac-val` (val), `bigmac-prod` (production). Key Lambdas: `appian-connector-{stage}-configureConnectors`, `-testConnectors`, and (val/production only) `-jiraNotifier`.
- `testConnectors` runs every minute from an EventBridge rule whose state comes from `healthCheckSchedule` in `infra/lib/environment-config.ts`. Master is `ENABLED`; val is `ENABLED`; production stays `DISABLED` until Task 18 of `docs/appian-connector-stability-plan.md` (restarts once locked the Oracle user). Disable the stage’s EventBridge rule to stop runs, and keep `healthCheckSchedule` in sync. It emits `{connectorName}_failures`, `_task_failures`, `_restart_capped`, `health_check_heartbeat` (every run), and `_restarts` before a restart (skip restart if that publish fails). It restarts non-RUNNING connectors except on Oracle auth/lock traces, at most `maxRestartsPerHour` (default 3) times per hour, and does not restart if it cannot read the restart count. Config sets `connection.attempts` to 1; it cannot push new credentials.
- From `tasks[].trace`: `ORA-01017`, `ORA-28000`, or `account locked` emit `{connectorName}_oracle_auth_failures` 1 and `_oracle_errors` 1 and skip restart; any other `ORA-` emits auth 0 and oracle 1 and keeps the restart rule; no Oracle trace emits 0 and 0.
- Connection alarms in `infra/lib/connector-alarms.ts` cover every name in `src/services/connector/libs/connector-names.json`: `appian-connector-{stage}-conn-{short}-connector-down`, `-task-down` (Max >= 1, 3 of 5), `-oracle-auth` (Sum >= 1, 1 of 1), `-restart-capped`, plus `-conn-health-check-missing` (only when the schedule is enabled) and `-conn-health-check-errors`. `{short}` drops the `source.jdbc.` prefix. All notify `Alerts-appian-alerts-{stage}` (email subscriptions are manual and must be confirmed; addresses are not committed). No alarm on `_oracle_errors`. CPU, memory, and log ERROR/WARN alarms must not use `-conn-`.
- In val and production, `appian-connector-{stage}-jiraNotifier` (reserved concurrency 1, two async retries, then SQS `-jiraNotifier-dlq` with an email alarm) handles `-conn-` ALARM/OK and ECS task-stopped events. It finds the open OY2 ticket with labels `macpro_appian_connector` and `{VAL|PROD}`, `statusCategory != Done`, and an exact summary match, then creates, comments on repeat, or comments on recovery (ticket stays open). Master has `jiraStageLabel: null` and no notifier. Fixed ticket fields live in `src/services/connector/libs/jira-ticket-config.ts`. Secret `appian/{stage}/jira` is JSON with `url` (`https://jiraent.cms.gov`, no trailing slash) and `token` (PEIT Bearer PAT); rotate by hand. Tickets use Epic Link `OY2-29580`, components `BigMAC` and `MACPro Appian`, Working Team Platform Submission, reporter/assignee `PEIT`.
- Existing JDBC source `source.jdbc.appian-connector-dbo-1` publishes to `aws.appian.cmcs.MCP_SPA_PCKG` (`timestamp+incrementing`, 5-minute poll). A second source for MACPro→SMART, `smartIntegrationConnector` (`source.jdbc.appian-connector-smart-1`), is live on master since 2026-10-27: it is in `connector-names.json` and the deployed `connectors` array with `tasks.max` 1, against aggregated view `MCP_SMART_INTG_AGGRTN_VW` → topic `aws.appian.cmcs.MCP_SMART_INTG_AGGRTN_VW` (every change event, `cleanup.policy=delete`, no Kafka message key, same `dbInfo`/schema and connector read-only login as `MCP_SPA_PCKG`, watermark `REPLICA_TIMESTAMP` only / mode `timestamp`). On 2026-10-28 both connectors were cut over on master from the Dev1 schema to `MACPROTEST1`: both topics were deleted and recreated with identical config, both connectors' JDBC offsets were reset by tombstoning their keys in `mgmt.connect.appian-connector-master.offsets` (the Confluent 6.0.9 worker has no Connect REST offsets API), and a clean full snapshot was verified (8,165 `MCP_SPA_PCKG` rows and 3,577 `MCP_SMART_INTG_AGGRTN_VW` rows). As of OY2-42881 (verified on `MACPROTEST1` 2026-11-10) the view has 20 columns including `CNSLTN_DT` and `SOURCE_SYSTEM`, and no longer has `PCKG_ID`, `SPA_PCKG_ID`, or `AUTHRTY_CD`. Note the `configureConnectors` PUT-then-restart can republish an uncommitted first batch for a brand-new connector; the SPA connector was re-created with a direct config PUT (no restart) to get an exact snapshot. Use a frozen custom `SELECT` (not `SELECT *`, all 20 verified view columns) and select CLOB columns `RU_JSON` / `REVIEWER_JSON` natively (kafka-connect-jdbc maps CLOB to a full string). Do not use `DBMS_LOB.SUBSTR` on them: this DB caps SQL `VARCHAR2` at 4000 (`MAX_STRING_SIZE=STANDARD`), so larger values error with ORA-06502 and 4000 silently truncates. Reaching Dev1 from the Kafka Connect worker previously required routes in both directions between the BigMAC data subnets and the Dev1 RDS subnet segment over the existing VPC peering, plus Oracle-port ingress from the BigMAC data range on the Dev data security group; that Dev1 access gate is superseded on master by the 2026-10-28 `MACPROTEST1` cutover. Do not release this connector to val/production until the view, SELECT grant, topic, and network path are confirmed per stage (target schemas there are `MACPROVAL0` and `MACPROP`). Spec: `docs/macpro-smart-appian-connector-spec.md`. Little data and days without rows are normal; do not add topic or row freshness alarms.
